## 前置：index.Map 字节流完整布局（实测 780 字节）

实测 index.Map 全文件 u32 流（195 个 u32，自文件偏移 0 起）：

    w[0]=176 w[1]=220 w[2]=1 w[3]=114 w[4]=176 w[5]=219 w[6]=1 w[7]=0 w[8]=31 w[9]=1 ...

**关键**：原版 sub_44004 的顺序读流（sub_44004 line 57-91）：

    ReadFile(lpFileName+245, 4)  -> 文件偏移 0..3  -> w[0]（写入 struct 字段 245）
    ReadFile(lpFileName+246, 4)  -> 文件偏移 4..7  -> w[1]（写入 struct 字段 246）
    ReadFile(&Buffer, 0x18=24)  -> 文件偏移 8..31 -> w[2..7]（6 字 表头）
    ReadFile(&v28, 4)           -> 文件偏移 32..35-> w[8]（记录数 v28）
    ReadFile(&Buffer, 24) xN    -> 文件偏移 36..  -> w[9..]（每条 6 字 = 24 字节控件记录）

- w[8]=31 是**真实的记录数**（v28），不是 w[4]=176。
- w[4]=176 是 **24 字节表头内的第 3 个 u32**（表头 6 字 = w[2..7]=[1,114,176,219,1,0]），不是记录数。

**Rust MapScene::parse 跳过前 16 字节（4 个 u32 = w[0..3]），因此 MapScene.words 数组相对全文件流左移 4 字：**

    MapScene.words[0] = w[4] = 176
    MapScene.words[1] = w[5] = 219
    MapScene.words[2] = w[6] = 1
    MapScene.words[3] = w[7] = 0
    MapScene.words[4] = w[8] = 31   <- 记录数，与原版 v28 完全一致
    MapScene.words[5..] = 控件记录

**结论：任务描述中 words[4]=176 是对全文件流 w[4] 的误读；MapScene.words[4] 实际为 31，与原版 v28 一致。**

## 核心问题 1：f5 分档 -> 渲染层（z-order）映射

### 1a. 原版是否按 f5 分档分层？

**否。原版不按 f5 分档。**

- sub_44004 line 92：for (i = 0; i < v28; ++i) -- 按文件顺序逐条读入，每条调 sub_449A8（line 104）插入同一链表（lpFileName+244）。
- sub_449C8 无任何 f5 分支；f5（控件类型）仅存入节点字段，**不参与分层或排序**。
- sub_443FC line 105-115 的链表遍历对全部节点无差别调用 sub_460F8，无 f5 分档逻辑。
- f5 在 sub_460F8 line 28（v7 = a1[7]）只决定**blit 例程变体**（1/2/3 模式 x 8/16 位 = 6 例程），不影响绘制顺序。

### 1b. 链表遍历顺序决定 z-order

sub_449C8 line 46-51（头插法，双端循环链表，哨兵头节点 a3）：

    v18 = *(_DWORD **)(a3 + 4);   // v18 = head->next = 当前首元素
    *v8  = a3;                    // 新节点.prev = 哨兵头
    v8[1] = v18;                  // 新节点.next = 旧首元素
    *v18 = v8;                    // 旧首元素.prev = 新节点
    *(_DWORD *)(a3 + 4) = v8;    // head->next = 新节点

推演插入序列（设哨兵头 H，初始 H.next=H，H.prev=H）：

| 步骤 | 插入 | head->next | H->prev（遍历起点） | 列表正序（next 方向） |
|------|------|-----------|---------------------|---------------------|
| 0 | - | H | H | H |
| 1 | R1 | R1 | R1 | H -> R1 -> H |
| 2 | R2 | R2 | R1 | H -> R2 -> R1 -> H |
| 3 | R3 | R3 | R1 | H -> R3 -> R2 -> R1 -> H |

sub_443FC line 105-115 遍历（**沿 prev 指针走**）：

    v15 = v1[244];   // 哨兵头 H
    v16 = *v15;      // v16 = H->prev = 第一次插入的节点 = R1（文件第 1 条）
    while (v16 != v15) {
        sub_460F8(v16 + 2, ...);
        v16 = *v16;  // v16 = v16->prev（沿 prev 走）
    }

遍历顺序：**R1 -> R2 -> R3 -> ... -> R31**（沿 prev 从尾到首 = 文件原始顺序）。

**z-order = 文件顺序**：第 1 条记录先 blit（底层），第 31 条最后 blit（顶层）。

### 1c. 对照 Rust 实现

crates/ti-app/src/sprite_atlas.rs line 222-238（blit_scene_frame）：

    for ctrl in &controls {   // 按文件顺序
        Self::blit_sprite(&sprite, ctrl.f2, ctrl.f3, fb, frame);
    }

MapControl::parse_words（crates/ti-formats/src/mapfile.rs line 82）按 i in 0..count 顺序读取，与文件顺序一致。

**Rust 与原版 z-order 一致（文件顺序）。正确。**

### 1d. index.Map 31 条的 z-order 实例

从实测数据（文件顺序 = w[9..] 起，每条 6 字）：

| 记录序号（文件顺序） | f1（精灵索引） | f2（X） | f3（Y） | 说明 |
|---|---|---|---|---|
| 1（底层） | 105 | 6 | 12 | 立绘/背景 |
| 2 | 105 | 22 | 34 | |
| 6-12 | 111 | 22..207 | 44 | 一排文字（Y=44 固定，X 递增 16） |
| 13-15 | 115,116,110 | ... | ... | |
| 16-19 | 117,108,109,113 | ... | ... | |
| 20-31（顶层） | 113 | ... | ... | |

**z-order 一句话结论**：按文件顺序逐个 blit，第 1 条（f1=105，Y=12）先画（底层），第 31 条（f1=113，Y=137）后画（顶层）-> **立绘在文字之下，文字压在立绘之上**。

## 核心问题 2：原版是否"分帧渲染"

### 2a. sub_443FC 遍历循环终止条件

sub_443FC line 105-115：

    v15 = v1[244];
    v16 = *v15;
    while (1) {
        if (v16 == v15) break;    // 唯一终止：走回哨兵头
        sub_460F8(v16 + 2, ...);
        v16 = *v16;
    }

**每帧遍历全部 31 个节点，无 10 件上限，无批计数。** 不存在"每帧放行一批 10 件精灵"的机制。

### 2b. sub_460F8 尾部 a1[12]/a1[11] 的真实语义

sub_460F8 line 108-121：

    if (a1[8] == 0) {          // a1[8] 为精灵派生字段（sub_449C8 中 = a4[8]）
        v20 = a1[12];
        a1[12] = v20 + 1;     // sub 计数 +1
        if (v20 == 9) {
            a1[12] = 0;
            a1[11] = v21 + 1; // batch 进位
        }
        if (a1[11] > a1[1])   // a1[11] 超过 a1[1]（总批数）则回绕
            a1[11] = 1;
    }

这是**每个精灵节点自己的**局部动画状态，不是全局批计数：
- a1[12]：sub（0..9，10 个子步）
- a1[11]：batch（精灵源裁剪段号，从 1 起）
- a1[10]：v12 = 精灵源裁剪宽度（由 sub_44004 line 103 派生）

裁剪窗（sub_460F8 line 86-95）：

    v14 = (a1[11] - 1) * a1[10];   // 源裁剪 X 起点 = (batch-1) x width
    v22[2] = v14;                   // src.x
    v22[3] = a1[10] * a1[11];      // src.w = width x batch（随 batch 增长）

**这是多帧动画精灵的源裁剪动画**：每个多帧精灵的源图按 X 方向分段揭示，每 10 帧推进一个 segment，batch 回绕到 1。**完全不是"每帧放行 10 件精灵"的全局帧轮转。**

### 2c. sub_45EC0 初值印证

sub_45EC0（节点描述符初始化）line 15-16：

    result[11] = 1;   // batch 初值 = 1（第一段）
    result[12] = 0;   // sub 初值 = 0

每个精灵独立初始化，与全局帧号无关。

### 2d. Rust 是否因此 z-order 错位？

**否。** Rust blit_scene_frame（sprite_atlas.rs line 222）每帧 blit 全部 31 条记录，与原版每帧遍历全部节点一致。Rust 用全局 self.frame()（elapsed_ms / FRAME_MS，100ms/帧）选多帧精灵的当前帧，原版用每节点的 a1[11]/a1[12] 独立计数 -- 两者对多帧动画的效果等价（都是约 10fps 推进），z-order 无错位。

## 核心问题 3：words[4]=176 count 字段损坏疑点

### 3a. sub_44004 如何消费 .Map 表头

sub_44004 对 .Map 文件的**顺序读流**（line 57-91）：

| 读操作 | 文件偏移 | 写入位置 | 实测值（index.Map） |
|--------|---------|---------|-------------------|
| ReadFile(lpFileName+245, 4) | 0..3 | struct 字段 245 | 176（场景宽） |
| ReadFile(lpFileName+246, 4) | 4..7 | struct 字段 246 | 220（场景高） |
| ReadFile(&Buffer, 0x18) | 8..31 | v30..v34（6 字表头） | [1,114,176,219,1,0] |
| ReadFile(&v28, 4) | **32..35** | **v28 = 记录数** | **31** |
| ReadFile(&Buffer, 0x18) x v28 | 36.. | 控件记录 | 31 x 6 字 |

**记录数 v28 在文件偏移 32..35（全文件流 w[8]），不是 w[4]。**

w[4]=176 是 24 字节表头（偏移 8..31）内的第 3 个 u32，与记录数无关。

### 3b. 原版按固定记录数读，不依赖 words[4]

sub_44004 line 91-92：

    ReadFile(FileW, &v28, 4u, ...);   // v28 = 记录数（从文件偏移 32 读）
    for (i = 0; i < v28; ++i) {       // 按 v28 读固定数量
        ReadFile(FileW, &Buffer, 0x18u, ...);
        sub_449A8(lpFileName + 244, v35);
    }

**原版完全依赖 v28（文件偏移 32）作为记录数，不使用 w[4]=176。**

### 3c. Rust MapControl::parse_words 用 words[4] 当 count 对不对？

crates/ti-formats/src/mapfile.rs line 72：

    let count = words[HEADER_WORDS - 1] as usize;  // = words[4]

MapScene::parse（line 130-152）跳过前 16 字节（4 u32），所以 MapScene.words 从全文件 w[4] 起。因此：

- MapScene.words[0] = w[4] = 176
- MapScene.words[1] = w[5] = 219
- MapScene.words[2] = w[6] = 1
- MapScene.words[3] = w[7] = 0
- **MapScene.words[4] = w[8] = 31**（记录数，与原版 v28 一致）

**Rust 代码是正确的。** MapScene.words[4]=31 = 原版 v28 = 31 条记录。

### 3d. "words[4]=176" 的误读来源

任务描述说 "index.Map words[:5]=[176,220,1,114,176]，words[4]=176"。这是**全文件 u32 流**（自偏移 0 起）的前 5 字，其中 w[4]=176 属于 24 字节表头（偏移 8..31）的一部分，**不是记录数**。

**正确映射**：
- 全文件 w[4]=176 -> MapScene.words[0]=176（表头第 1 字，Rust 当精灵宽处理，语义存疑但解析不依赖它）
- 全文件 w[8]=31 -> MapScene.words[4]=31（**记录数，Rust parse_words 用的这个**）

**Rust 不需要改。** MapControl::parse_words 用 MapScene.words[4]=31 作为 count，与原版 v28 完全对应。

### 3e. 字节数校验

    文件 780 字节（原版读流角度）：
    4(lpFileName[245]) + 4(lpFileName[246]) + 24(表头) + 4(v28) + 31x24(记录)
    = 4 + 4 + 24 + 4 + 744 = 780  [OK]

    MapScene 视角（跳过 16 字节固定头）：
    MapScene.words 长度 = (780 - 16) / 4 = 191 字
    = 4(表头 w[4..7]) + 1(v28 = w[8]) + 31x6(记录)
    = 4 + 1 + 186 = 191  [OK]

    parse_words 校验：
    HEADER_WORDS + count x FIELDS = 5 + 31 x 6 = 5 + 186 = 191 = words.len()  [OK]

## 推测标注

- a1[10] 是"精灵源裁剪宽度"（由 sub_44004 line 103 派生）-- **推测**，IDA 未展开 Buffer 完整来源；从 v22[2]=(batch-1)xa1[10] 的裁剪语义反推。
- 表头 6 字中 w[4]=176, w[5]=219 是"精灵文件宽高" -- **推测**，sub_44004 line 86-89 用 lpFileName[245]/sprite_w 算 tile 数，但未直接读到精灵宽高字段。
- sub_44828 在 sub_443FC **之后**调用（sub_117D4 line 68-73：sub_443FC(a1); sub_44828(a1, ...)），所以数字字形 blit 在全部 31 条控件之后 -> **数字字形压在控件之上（顶层）**。这是可推演的调用顺序，非推测。
