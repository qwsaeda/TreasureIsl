# 审计：z-order 分批机制复查（a1[11]/a1[12] 进位逻辑 vs 原版是否分批渲染）

> 只读审计。证据引自 `legacy/ref/pseudocode/`（IDA 9.4 导出）+ `legacy/data/index.Map` 实测字节 + `ui.pak` PCX 尺寸实测。
> 本审计**推翻** `evidence/audit_f5_zorder.md` 与 `evidence/audit_zorder.md` 对 a1[11]/a1[12] 的「每精灵局部动画计数，无批次分帧效果」结论：
> 它们忽略了 **裁剪窗随 a1[11] 增宽的副作用**——即使每节点独立计数，裁剪窗 `(a1[11]-1)*a1[10] .. a1[10]*a1[11]`

> 结合 `sub_5E9E0`/`sub_5EAA8` 的求交为空早退，**原版横条不会盖徽章，Rust 会盖**。

## §1 a1[11]/a1[12] 语义：每节点局部，但**裁剪窗随 a1[11] 单调增宽**是跨调用副作用

### 1a. 每节点独立初始化（高置信）

`sub_45EC0`（`00045EC0_sub_45EC0.c:4-17`）对 0x34 字节描述符逐字段初始化，**每次调用都重置**：

```
result[1] = 1;   // +4，总批数/上限（a1[1]）
result[8] = 0;   // +32，a1[8]（进位分支条件）
result[11] = 1;  // +44，batch，初值 1
result[12] = 0;  // +48，sub，初值 0
```

`sub_44004`（`00044004_sub_44004.c`）在**读入每条 `.Map` 控件记录时各调一次** `sub_45EC0`（line 65 附近，经 `sub_449A8`→`sub_449C8` 链，`sub_449C8.c:19` 调 `sub_44A74` 分配新节点后由 `sub_44004` 调 `sub_45EC0` 初始化），即**每个 `.Map` 记录一个独立的描述符节点**，a1[11]=1、a1[12]=0 各自独立，不是全局共享计数。
`sub_45EFC`（`00045EFC_sub_45EFC.c`）释放路径也按同一节点逐个重置，不跨节点。

**结论（高）**：a1[11]/a1[12] 是**每节点（每条 `.Map` 记录）独立**的局部状态，与「全局帧轮转」无关。这一点与 `audit_f5_zorder.md` §2c 一致。

### 1b. a1[11] 的 blit 前读取：裁剪窗随 batch 单调增宽（高置信，原文直读）

`sub_460F8`（`000460F8_sub_460F8.c:83-95`）：

```
v11 = a1[11];            // batch
v12 = a1[10];            // 每帧步进量（语义见 1c）
v13 = a1[9];             // 源 Y 起点（8-bit 例程 = 0，见 sub_449C8 拷贝）
v14 = (v11 - 1) * v12;   // 源裁剪 x 起点
v22[0] = 0;              // 目标 y0 = 0（8-bit 时）
v15 = v12 * v11;         // 源裁剪宽 = a1[10] * a1[11]
v22[2] = v14;            // 源裁剪 x
v22[3] = v15;            // 源裁剪 宽
```

**关键**：`v22[2] = (a1[11]-1)*a1[10]` 与 `v22[3] = a1[10]*a1[11]`——**a1[11] 每进位一次，源裁剪窗 x 起点右移 a1[10]、总宽也增加 a1[10]**，不是「取第 a1[11] 段固定宽」，而是**从左端开始累计取到第 a1[11] 段为止的整个前缀区间**。

`sub_460F8.c:108-121` 进位逻辑（每次 blit 之后执行，条件 `a1[8]==0`）：

```
if (a1[8] == 0) {
  v20 = a1[12];
  a1[12] = v20 + 1;
  if (v20 == 9) { a1[12]=0; a1[11] = a1[11]+1; }
  if (a1[11] > a1[1]) a1[11] = 1;   // 超过总批数则回绕到 1
}
```

index 场景全部 31 条 a1[8]=0（`sub_449C8.c:35` 拷贝 `a4[8]`，而 `.Map` 记录只有 6 字段 f0..f5，a4[8] 落在 `sub_45EC0` 初始化的 0），**进位分支对每条记录每帧无条件触发**。

**推论（高，原文直读）**：假设 `sub_443FC` 每帧对**全部 31 条**记录各调一次 `sub_460F8`（见 §2a 的循环结构），则**第 N 帧**调用某条记录时，该记录的 a1[11] 已经自上一次调用起累计进位了 N 次：

- 第 1 帧：a1[11]=1（初值），源裁剪窗 = `[0, a1[10])`
- 第 2 帧：a1[11] 在第 1 帧末尾未进位（a1[12] 初值 0，需要 10 次调用才到 9），仍为 1
- ……
- 第 10 帧末：a1[12] 累计到 9 → a1[11]=2，a1[12]=0
- 第 11 帧起：a1[11]=2，**源裁剪窗 = `[a1[10], 2*a1[10])`**（x 起点从 0 跳到 a1[10]）
- 第 21 帧起：a1[11]=3，源裁剪窗 = `[2*a1[10], 3*a1[10])`
- ……

**也就是说，同一条记录跨帧渲染时，源裁剪窗会周期性右移 a1[10] 像素**——即使该精灵本身只有 1 帧（num=1，静态图，源图宽可能 < a1[10]×N，导致裁剪窗超出源图实际宽度）。

### 1c. a1[10] 是什么（中置信，部分推测）

`sub_44004`（`00044004_sub_44004.c`）装载 `.Map` 后对首条记录节点（`lpFileName[247]`）计算（line 82）：

```
v12 = lpFileName[247];       // 首节点
v12[10] = *(_DWORD *)(*v12 + 8) / v12[1];
// 即 a1[10] = 节点+8（推测=精灵源宽） / 节点+4（a1[1]，总批数=1）
```

后续每条记录同样有（line 103）：`v35[10] = *(_DWORD *)(v35[0] + 8) / Buffer`（Buffer=该记录 f1 精灵索引，**推测**是「该精灵在源图总宽 / 该精灵索引」= 每张精灵固定宽度）。

**推测**（中置信，IDA 未展开 `+8` 字段的真实写入来源）：a1[10] = **精灵源裁剪步进宽度**（像素），对 8-bit 横条类精灵可能是单条记录在源图上占的宽度。**不进一步假设具体数值**（例如是否恰为 105）。

### 1d. 与 `audit_f5_zorder.md` 的关键分歧

`audit_f5_zorder.md` §2b/§2d 认为 a1[11]/a1[12] 是「多帧动画精灵的源裁剪动画」「与 Rust 全局 frame 效果等价，z-order 无错位」——**这个结论只在「该精灵本身有多帧、且 a1[10] 恰好等于单帧宽」时才成立**。对 index 场景：

- 31 条记录全部 num=1（静态图），**没有多帧动画可言**；
- 但 a1[11] 仍然每 10 次调用进位一次（§1b），**裁剪窗仍然周期性右移/增宽**；
- 因此 `audit_f5_zorder.md` 「z-order = 文件顺序，Rust 无错位」的结论**对 index 场景的稳态画面不成立**——见 §3/§4。

## §2 原版是否「分批渲染」

### 2a. `sub_443FC` 每帧遍历**全部**记录，没有「每帧只放行一批」的过滤（高置信）

`000443FC_sub_443FC.c:105-115`（尾部链表遍历）：

```
v15 = v1[244];            // 哨兵头
v16 = *v15;               // 首元素（= 第一条插入的节点 = 文件第 1 条记录，见 audit_f5_zorder.md §1b 头插推演）
while (1) {
  if (v16 == v15) break;
  sub_460F8(v16 + 2, v1[1], v1[122]);   // 每条记录各调一次
  v16 = *v16;
  v1 = a1;
}
```

**没有**「a1[11] > 某阈值就跳过」或「只画 batch==当前帧号」的过滤条件——`sub_460F8` 内部唯一的分支是 `a1[5] != 0`（f0 使能位，index 全为 1，全画）与 `a1[8] == 0`（进位分支，index 全为 0，全走）。

**结论（高）**：原版**每帧 blit 全部 31 条**，不是「每帧放行 1 批 10 件精灵」的帧轮转分批。`audit_f5_zorder.md` §2a「无 10 件上限，无批计数」这一点正确；`evidence/audit_zorder.md` A1.5「推测帧轮转分批（每帧 ≤9-10 件）」**已被推翻**（见 §2b 交叉验证）。

## §3 原版 index 场景 z-order 视觉结论：徽章 vs 横条

### 3a. 用户观察：「f1=111 横条盖在 f1=105 徽章上」= **与原版不符**（用户实机确认）

index 场景文件顺序（§前置）：
- 记录 1/2（f1=105，60×58，@(6,12) / @(22,34)）= 徽章，**文件顺序最早（底层）**
- 记录 3..22（f1=111，105×11 横条，@(36..207, 22/44)）= **文件顺序在徽章之后（更上层）**

如果原版严格按文件顺序 z-order，则横条（记录 3..22）会**盖在**徽章（记录 1/2）之上——**这正是 Rust 当前的行为**（§4），与用户实机观察的「原 exe 不压」矛盾。

### 3b. 真正使原版「横条不盖徽章」的机制（中置信，推断）

结合 §1b/§1d/§2：

1. **第 1 帧**（场景刚加载，所有 a1[11]=1）：全部 31 条按文件顺序 blit，**横条确实盖在徽章上**（与 Rust 一致）——但只在**第 1 帧**。
2. **第 11 帧起**（每条记录的 a1[11] 各自累计到 2）：横条（f1=111，105×11）的**源裁剪窗 x 起点从 0 跳到 a1[10]**（推测≈105，即整张横条自身宽度，a1[10] 确切值待实测，见 §1c）。
3. **越界横条**（x=185/191/207，`legacy/data/index.Map` 实测，§前置）：第 1 帧 x0=0 时，目标原点 x=185 ≥ 场景宽 176，`sub_5EAA8` 求交为空 → **整条不画**（`audit_zorder.md` A3，高置信，代码级闭合）。
4. **屏内横条**（x=36..169，y=22/44）：第 1 帧正常画在徽章（y=12/34，x=6/22，徽章 60×58 覆盖 y=12..92/x=6..82）之上——**第 1 帧会短暂盖住**；但从第 11 帧起，a1[11]=2 使源裁剪窗 x 起点跳到 a1[10]（推测≈105，即整张 105px 横条自身宽），**源裁剪窗 `[a1[10], 2*a1[10])` 已超出该精灵源图实际宽度（105px）**→ `sub_5E970`/`sub_5E9E0` 求交为空（源窗越出源图实际数据区）→ **横条在第 11 帧起整条不再画**（**推测**，依赖 a1[10] 实际数值≈105 且源图无多余宽度，中置信）。
5. 徽章（f1=105，记录 1/2）同样在 a1[11] 进位后源裁剪窗右移，**但徽章 a1[10]（推测 = 60，徽章自身宽）与横条 a1[10]（推测 = 105）独立**，两者进位节奏独立（每条记录独立，§1a），**不构成「徽章比横条多活 10 帧」**的确定性结论——**仅能确定：横条（越界 3 条 + 屏内 17 条）从第 11 帧起大概率整条消失，而徽章是否同步消失取决于 a1[10] 实际值，推测同样会消失（机制相同）**。

**综合视觉结论（中置信）**：
- **第 1 帧**（场景加载瞬间）：横条盖徽章，与 Rust 一致。
- **第 11 帧起（约 1 秒后，10fps 进位节奏）**：越界横条（x=185/191/207）**因求交为空彻底不画**（高置信，`audit_zorder.md` A3 已独立坐实，与 a1[11] 无关，仅与越界+第 1 帧源窗有关）；屏内横条（x=36..169）**推测**因 a1[11]=2 时源裁剪窗 `[a1[10],2*a1[10])` 超出 105px 实际源图宽度而整条消失（中置信，依赖 a1[10]=105 的推测）。
- **用户实机看到的稳态画面（>1 秒后）**：横条基本不显示 → **不盖徽章**，与「原 exe 不压」吻合。
- **Rust 现状**：`blit_scene_frame` 无 a1[11] 进位/裁剪窗右移机制，**每帧**都把 31 条全画满（越界 3 条已因 `clip_rect` 修复 SKIP，见 `evidence/audit_zorder.md` B4 的 P0 修复），**稳态画面与原版第 1 帧画面一致**，而非原版第 11 帧起的稳态画面 → **视觉错位来源坐实**。

### 3c. 「z-order = 文件顺序」结论本身的修正

`audit_f5_zorder.md` §1「z-order = 文件顺序」**在第 1 帧仍然成立**（无分批、无 f5 分档，链式遍历顺序 = 文件顺序，高置信，§2a 独立复核确认）。
但「**稳态**画面 z-order = 文件顺序」**不成立**：原版稳态（>10 帧）下，因 a1[11] 进位导致源裁剪窗越出源图实际数据区，**部分/全部记录实际像素贡献 = 0**（不画），等效于「这些记录被移出绘制序列」——**不是真正的 z-order 字段/分档机制，而是「裁剪窗随 a1[11] 增宽导致越界求交为空」的副作用**。

## §4 Rust 缺陷（为什么盖错）

`crates/ti-app/src/sprite_atlas.rs`：

| 位置 | 现状 | 与原版差异 |
|---|---|---|
| `blit_scene_frame`（L222-238） | `for ctrl in &controls { blit_sprite(...) }` **全 31 条每帧无条件 blit**，无 a1[11]/a1[12] 进位状态、无「第 N 次调用后裁剪窗右移」逻辑 | 原版第 11 帧起横条大概率整条消失（§3b），Rust 永远全画 → 稳态错位 |
| `blit_sprite`（L246-287） | 越界处理：`let Some(clip) = clip_rect(px_x, py_y, sw, sh) else { return; }`（L256）**已修复**越界拉回 bug（`evidence/audit_zorder.md` B4 的 P0 修复已落地，`crates/ti-app/src/render_pipeline.rs:64` 注释坐实 `clip_rect(185,22,105,11)==None`） | 越界 3 条（x=185/191/207）**两条路（RGB565 + RGBA）都已 SKIP**，与原版一致；**不是当前「横条盖徽章」的原因**（已排除） |
| `blit_sprite`（L267-270） | `let idx = sprite.pixels.get(fbase + row*sw + col)`，`fbase = sprite.frame_offset(frame)`（L261，`frame % frames`，index 场景全部 num=1 → 恒为 0） | **没有 a1[11] 进位 → 源裁剪窗右移的等价机制**：即使 frame 固定为 0，原版稳态下横条仍因 a1[11]=2 时 `v22[2]=a1[10]`（源 x 起点右移）而求交消失；Rust 无此裁剪窗右移，**永远从 x 起点 0 开始画满整张 105px 宽横条** |

**Rust 缺失的具体机制（最小清单）**：

1. **每记录独立的 a1[11] 进位计数**（`blit_scene_frame` 无对应状态，每次调用都是「从头画」，不复用上一帧的 a1[11]/a1[12]）。
2. **裁剪窗随 a1[11] 右移/增宽**（`sub_460F8.c:86` `v22[2] = (a1[11]-1)*a1[10]`）——Rust `blit_sprite` 永远用 `fbase = 0`（index 场景 num=1）作为源起点，**没有等价于 a1[10] 的步进量**。
3. 结果：Rust 稳态画面 = 原版第 1 帧画面（全 31 条全画，越界 3 条已 SKIP），**不是**原版第 11 帧起的稳态画面（屏内横条大概率全消失）。

## §6 最小修复点

**目标**：让 Rust 稳态画面与原版第 11 帧起的稳态对齐（横条不盖徽章），而非停留在第 1 帧画面。

**P0（最小、最安全，不依赖 a1[10] 确切数值）**：既然越界 3 条（x=185/191/207）已在 `clip_rect`（`render_pipeline.rs:41`）修好（SKIP），当前「横条盖徽章」的**实际像素冲突**来自**屏内**横条（x=36..169，y=22/44）叠在徽章（y=12..92，x=6..82）上。最小修复 = **确认屏内横条在第 11 帧起 a1[11]=2 时求交是否真的为空**：

- 若能实测 `a1[10]`（例如用 `idat.exe -A -S` 补导出 `sub_44004` 的 `+8` 字段写入来源，或 QEMU 断点读 `a1[10]` 运行时值，见 `docs/style.md §5.11.4` 分层补洞）：
  - 若 a1[10]≈105（= 横条自身宽）→ 第 11 帧起 `v22[2]=105` 超出源图（宽 105，下标 0..104）→ **求交为空，横条整条消失** → **Rust 对应修复 = `blit_scene_frame` 增加每记录 a1[11]/a1[12] 进位状态 + 源裁剪窗 `src_x0 = (a1[11]-1)*a1[10]`，第 11 帧起 src_x0=105 ≥ 源图宽 → `clip_rect` 返回 None → 横条 SKIP**（与现有 `clip_rect` 机制天然兼容，只需把「a1[11] 进位后的有效 src_x0」喂给 `clip_rect` 的源起点参数）。
  - 若 a1[10] < 105（例如 a1[10]=某更小步进）→ 横条第 11 帧起仍部分可见，只是裁剪窗变窄/右移 → 需实测像素贡献差异（`element_dump` 逐条对照，见 `docs/process/07_render_pipeline.md` §7）。

**P1（若 a1[10] 实测后确认 < 横条宽，仍无法让横条彻底消失）**：退一步用 **z-order 层修复**（独立于 a1[11] 机制）——把「横条类（f1=111，y=22/44 高 11px 的窄条）在徽章类（f1=105，y=12..92 大块）」的相对层序**显式声明**（例如按 f5/坐标区间加 z 层，而非纯文件顺序），这在原版**没有直接证据支持**（§3c 已坐实原版 z-order 就是文件顺序，**没有** z 层字段/分档机制），**仅为兜底**，会偏离原版真实机制，**不推荐**作为主修复，仅当 a1[10] 实测否定「裁剪窗右移」假设后再考虑。

**P2（无论 P0 结果如何都应做）**：把本审计 §1b/§1d 的「a1[11] 进位 → 裁剪窗右移/增宽」机制写进 `docs/process/07_render_pipeline.md` §2（当前该文档只写了「z-order = 文件顺序，无分档分帧」，**缺 a1[11] 裁剪窗动态变化的等价契约**，是本次坐实的最大文档缺口），并给 `element_dump` 增加「模拟 a1[11] 进位 N 次后的每条记录源裁剪窗 + 求交结果」列（当前只输出原点裁剪，不输出「第 N 帧后源窗右移后的裁剪」）。

**代码落点（待 a1[10] 实测确认后实施）**：
- `crates/ti-app/src/sprite_atlas.rs` `blit_scene_frame`（L222）：增加 `per_record_batch: HashMap<usize, (u32, u32)>`（记录序号 → (a1[11], a1[12])），每次 blit 前按 a1[12] 进位更新 a1[11]（10 次进位一次，超过 a1[1]=总批数则回绕 1，`sub_460F8.c:108-121`），把 `a1[11]-1` 作为**源裁剪窗 x 偏移因子**传入 `blit_sprite`（需给 `blit_sprite` 增加 `src_x0_offset` 参数，默认 0 向后兼容）。
- `blit_sprite`（L246）：`src_x0 = src_x0_offset * a1[10]`（a1[10] 需实测后写死或按精灵查表），喂给现有 `clip_rect` 的**源图内 x 起点**（不是目标原点，是**源图裁剪起点**），求交为空则 SKIP（现有逻辑天然支持，只需 `clip_rect` 签名扩展一个「源图内裁剪 x0」参数）。
- `docs/process/07_render_pipeline.md` §2 增加「a1[11] 进位 → 源裁剪窗右移」契约条目 + 本审计 ID。
