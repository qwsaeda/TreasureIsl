- [ ] 理解三种坐标系：世界坐标、屏幕坐标、本地坐标

- [ ] 理解摄像机的作用（视野矩形：位置 + 放大倍率）

- [ ] 理解逻辑分辨率 vs 物理分辨率

- [ ] 说清"世界 / 画布 / 物理屏幕"三个空间的关系与单位

## 核心概念

### 为什么需要多个坐标系

游戏世界里有很多"位置"，但它们不在同一个空间里：

```
世界坐标：玩家站在地图的哪个点
屏幕坐标：玩家画在屏幕的哪个位置
本地坐标：按钮在面板内的相对位置
```

如果用同一个坐标表示所有东西，地图移动、窗口缩放、UI 嵌套都会变成噩梦。**不同层次用不同坐标，变换负责翻译。**

---

### 先打通全局：三个空间的关系

**这一步是全章的地基，务必先看懂。**

```
┌────────────────┐     ┌────────────────┐     ┌────────────────┐
│   世界坐标       │     │   逻辑画布       │     │   物理屏幕       │
│                │     │                │     │                │
│  地图 = 世界     │ ──→ │ 画布 = 拍下来   │ ──→ │ 屏幕 = 印的纸   │
│  256 × 256 格   │     │  的一张照片     │     │  640 × 480 像素 │
│                │     │  176 × 220 像素  │     │                │
└────────────────┘     └────────────────┘     └────────────────┘
        ↑                      ↑                      ↑
   ① 摄像机取景              ② 视口放大
   （含等距投影）            （乘 scale 加 offset）
```

**比喻串起来**：

```
  地图   = 整张城市地图（很大）
  摄像机 = 手里的取景框（只框住一小块）
  画布   = 取景框里拍下来的那张照片（176×220）
  屏幕   = 把照片印出来的大相纸（640×480）
```

**关键结论：画布 ≠ 地图**

```
  进画布之前 → 单位是「格」（逻辑地图格子）
  进画布之后 → 单位是「像素」，不再有地图概念

  画布 176×220 比地图 256×256 "小"！因为只装了视野那一小块
  屏幕 640×480 比画布 "大"，因为放大印出去了
```

**所以第 ② 步就是渲染流水线**（详见第 7 章 + `docs/process/07_render_pipeline.md`）：

```
  世界 ──摄像机──→ 画布 ──渲染到屏幕──→ 物理屏幕
       格子          像素              像素
     （逻辑）      （逻辑）         （物理像素）

  前半段 = 几何变换（本章讲的）
  后半段 = 光栅化 + 上传（第 7 章讲的）
```

### 坐标系 1：世界坐标（World Space）

**生活类比：城市地图上的地址**

```
想象一张巨大的城市地图铺在地上，256米 x 256米。

   (0,0) ─────────────────→ x
     │
     │    你在 (128, 64)
     │    学校在 (200, 150)
     │    公园在 (50, 200)
     ↓
     y

你的地址 (128, 64) 是绝对的：
  不管谁来地图上看，你的位置不变。
  不管用多大的屏幕看，你的位置不变。
  你的位置只取决于你在地图上的哪里。
```

**特点**：
- 与屏幕无关，地图不动坐标就不变
- 地图可以很大（256x256），但屏幕只能显示一小块
- 玩家移动 = 世界坐标变化
- 游戏逻辑（碰撞检测、移动规则）用世界坐标

---

### 坐标系 2：屏幕坐标（Screen Space）

**生活类比：你视野里的位置**

```
你站在地图前，眼前有一个矩形视野（比如 176x220 像素）。
你通过视野看地图，只有视野范围内的东西才看得见。

假设视野左上角对准地图 (118, 54)：

  视野左上角 ───────────→ x
     │
     │    你（地图 128, 64）在视野的 (10, 10)
     │    公园（地图 50, 200）在视野外（太偏，看不到）
     │    学校（地图 200, 150）在视野的 (82, 96)
     ↓
     y

你的视野位置 (10, 10) 是相对的：
  你向右转头 → 你在视野里的位置向左移动
  你凑近看 → 你在视野里的位置向外推
  你后退 → 你在视野里的位置向中心缩
```

**特点**：
- 只有视野范围内的坐标才有意义
- 视野移动/缩放，同一世界物体的屏幕坐标会变
- 渲染用屏幕坐标（画在视野的哪个位置）
- 视野范围外的东西不画

---

### 坐标系 3：本地坐标（Local Space）

**生活类比：剧院里的座位号**

```
你在剧院第 3 排第 5 号。
这个位置是相对于剧院的，不是相对于城市的。

  如果剧院搬到别的地方：
    你的座位号不变（还是第 3 排第 5 号）
    但你在城市里的绝对位置变了

  如果剧院里的座位重新排列：
    你的座位号变了（变成第 4 排第 6 号）
    但剧院在城市里的位置不变
```

**游戏中的应用**：
```
面板在屏幕 (100, 100)，按钮在面板内 (10, 20)
  按钮的本地坐标 = (10, 20)
  按钮的屏幕坐标 = (100 + 10, 100 + 20) = (110, 120)

移动整个面板到 (200, 200)：
  按钮的本地坐标不变 = (10, 20)
  按钮的屏幕坐标变了 = (200 + 10, 200 + 20) = (210, 220)
```

**特点**：
- UI 嵌套时，每个控件用本地坐标
- 父容器负责变换（移动面板，按钮自动跟随）
- 移动整个面板，按钮本地坐标不变

### 变换 1：世界 → 屏幕（摄像机变换）

**相机 = 人眼的视野矩形**

```
人眼不动，眼前有一个矩形视野：
  凑近看 → 视野里看到的地图区域变小，但物体更大（放大）
  拉远看 → 视野里看到的地图区域变大，但物体更小（缩小）

相机参数只有两个：
  1. 视野矩形对准地图的哪个位置
  2. 视野矩形放大还是缩小
```

**为什么不是一个系数直接转换**：

```
同一个点 A (50, 30)：
  视野左上角对准 (40, 20) → A 在视野 (10, 10)
  视野左上角对准 (0, 0)   → A 在视野 (50, 30)
  视野左上角对准 (50, 30) → A 在视野 (0, 0)（A 正好在视野左上角）
  视野左上角对准 (40, 20) 且 zoom=2 → A 在视野 (20, 20)

同一个点，视野位置不同、zoom 不同，在视野里的位置不同。
所以必须知道视野的位置和 zoom，不能固定一个系数。
```

**一个点是怎么转换的（看图）**：

已知条件（三幅图共用）：
```
点 A 在世界坐标 (50, 30)
视野左上角对准世界 (40, 20)
```

#### ① 世界（从上往下看）

```
        x →
      0 ┼──────────────────────────────────────
        │              整个世界 256x256
        │              视野只是其中一小块
        │
     20 ├──────────┬─────────────────┬───────────
        │          │ ← 视野左上角      │
        │          │   对准 (40,20)   │
        │          │        ● A       │
        │          │      (50,30)     │
        │          │                 │
        │          └─────────────────┘
        ↓
```

#### ② zoom = 1：A 落在视野的哪里

```
        x →
      0 ┼──────────────────────────────
        │ ● A
        │ │
     10 ├─╂────────────
        │ │
        │ │
        │ │
        │ │
        ↓

      量法（只做减法）：
        A 离视野左边  50 − 40 = 10
        A 离视野上边  30 − 20 = 10
                   → A 在视野 (10, 10)
```

#### ③ zoom = 2：同一个 A，被推得更远

```
        x →
      0 ┼──────────────────────────────
        │
        │       ● A
        │       │
     20 ├───────╂──────────
        │       │
        │       │
        │       │
        │       │
        ↓

      量法（减完再乘）：
        10 × 2 = 20
        10 × 2 = 20
                   → A 在视野 (20, 20)

      看图要点：
        A 在图 ② 里紧贴左上角，在图 ③ 里被推到斜下方。
        点没动，是"看到的范围变小、东西变大"把它顶开的。
```

#### 三幅图串起来 = 两步公式

```
世界 ──① 减去视野左上角──→ 相对距离 ──③ 乘 zoom──→ 视野坐标
       (50−40, 30−20)          (10, 10)      ×1 →  (10, 10)
                                          ×2 →  (20, 20)
                                          ×0.5→  (5, 5)
```

总结公式：
  屏幕 x = (世界 x - 视野位置 x) × zoom
  屏幕 y = (世界 y - 视野位置 y) × zoom

**关键理解**：
- 平移 = 减去视野左上角坐标（把视野原点移到屏幕原点）
- 缩放 = 乘 zoom（放大 = 距离变大，缩小 = 距离变小）
- 两步缺一不可：不平移不知道相对位置，不缩放不知道大小

### 变换 2：屏幕 → 物理像素（视口变换）

**生活类比：把照片印在不同大小的纸上**

```
你的视野是 176x220 像素（逻辑分辨率）。
但你的手机屏幕是 640x480 像素（物理分辨率）。
你的电脑屏幕可能是 1920x1080 像素。

同一张"照片"（视野画面），印在不同大小的纸上，方法不同：
  纸比照片大 → 放大照片，两边留白边
  纸比照片小 → 缩小照片，上下留白边
  纸和照片一样大 → 直接印

问题：怎么印才不会变形？
```

**为什么不是简单乘系数**：

```
逻辑分辨率 176x220，宽高比 176:220 = 0.8
物理分辨率 640x480，宽高比 640:480 = 1.33

如果直接乘系数：
  宽方向：640 / 176 = 3.64 倍
  高方向：480 / 220 = 2.18 倍

  宽乘 3.64，高乘 2.18 → 画面被拉宽变形！

正确做法：等比缩放（取小的倍率）+ 居中留白边
```

**完整推导（看图）**：

已知条件：
```
逻辑画面 176 x 220    （照片原尺寸）
物理屏幕 640 x 480    （纸的大小）
```

#### ① 直接乘会变形

```
     照片 176x220            直接拉宽到 640x480
   ┌────────────┐          ┌──────────────────────┐
   │            │          │                      │
   │    圆 ○     │   宽×3.64                │    ○     │  ← 圆被压扁了
   │            │  高×2.18 │                      │
   └────────────┘          └──────────────────────┘
     176 x 220               640 x 480

   scale_x = 640/176 = 3.64   ← 宽放大得多
   scale_y = 480/220 = 2.18   ← 高放大小
   两个倍率不一样 → 变形
```

#### ② 取小的那个，等比放大

```
   scale = min(3.64, 2.18) = 2.18   （两边都用这一个数）

     照片等比放大 2.18 倍
   ┌────────────────────┐   宽 176×2.18 = 384
   │                    │   高 220×2.18 = 480
   │                    │   → 宽比屏幕窄，高刚好
   └────────────────────┘
```

#### ③ 居中留黑边

```
        物理屏幕 640 宽
  ┌────────────────────────────────────────┐
  │░░░░░░░░░░░░┌──────────────────┐░░░░░░░░░│
  │░░░░░░░░░░░░│   画布放大 2.18   │░░░░░░░░░│
  │░ 黑边 128 ░│   宽 384          │░ 黑边128░│
  │░░░░░░░░░░░░│   高 480（刚好满） │░░░░░░░░░│
  │░░░░░░░░░░░░└──────────────────┘░░░░░░░░░│
  └────────────────────────────────────────┘
        offset_x = (640 − 384) / 2 = 128
        offset_y = (480 − 480) / 2 = 0
```

#### ④ 变换：先缩放，再加黑边

```
   逻辑 (10, 10)
       │
       │ × 2.18        缩放
       ▼
   (21.8, 21.8)
       │
       │ + (128, 0)   跳过左边黑边
       ▼
   物理 (149.8, 21.8) ≈ (150, 22)
```

**总结公式**：
```
  scale = min(物理宽/逻辑宽, 物理高/逻辑高)
  offset_x = (物理宽 - 逻辑宽 × scale) / 2
  offset_y = (物理高 - 逻辑高 × scale) / 2
  物理 x = 逻辑 x × scale + offset_x
  物理 y = 逻辑 y × scale + offset_y
```

**为什么叫"等比"**：宽和高用同一个 `scale`，画面不变形。
代价是多出来的方向留黑边（letterbox）。

### 黑边是"选择"的结果：4 种缩放模式

黑边不是 bug，是 `Smooth` 模式的**主动选择**。本项目实现了 4 种
（`crates/ti-platform/src/settings.rs:17`）：

```
Smooth（本章上面讲的）              ZoomCrop（现代手游最常用）
┌──────────────────────┐          ┌──────────────────────┐
│░░░░┌────────────┐░░░░│          │┌──────────────────┐│
│░░░░│            │░░░░│          ││                  ││
│░░░░│  176×220   │░░░░│          ││   放大铺满        ││
│░░░░│            │░░░░│          ││                  ││
│░░░░└────────────┘░░░░│          ││  溢出裁掉 ↗      ││
└──────────────────────┘          ││                  ││
 黑边 128 + 128                   │└──────────────────┘│
                                 └──────────────────────┘
                                 无黑边，但左右内容被切掉
```

| 模式 | 做法 | 有黑边？ | 副作用（实测依据见 `settings.rs` 注释） |
|---|---|---|---|
| `Smooth`（默认） | 等比缩放 + 居中留边 | **有** | 无 |
| `Integer` | 等比但对齐到整数倍 | **无** | 像素锐利，不模糊 |
| `Stretch` | 宽高各拉各的，填满 100% | **无** | **画面变形** |
| `ZoomCrop` | 等比放大到铺满，溢出的**裁掉** | **无** | 边缘视野变少（4:5 → 20:9 约裁 44% 宽） |

**为什么现在的手机游戏基本没黑边**：

```
  主流做法（正是 ZoomCrop / Stretch）：
    宁可裁掉一点边缘内容，也不要两侧黑边（黑边显得廉价）

  更彻底的做法（现代引擎常见）：
    干脆不设固定画布，直接按设备原生分辨率渲染
    UI 用锚点贴边（吸边），中间区域才是游戏内容

  本项目走的是"固定画布 + 可选缩放模式"这条较传统的路
  （为了对齐原版 176×220 的像素布局）
```

### 贴图怎么填满一格：`FilterMode`

前面讲了"1 格 = 32×16 像素"。那**贴图的像素怎么填进这 32×16**？
这是采样规则问题，本项目有 2 种（`crates/ti-platform/src/settings.rs:269`）。

**下面用数字当亮度（0=黑，9=白），把每个像素的实际值直接列出来。**

#### 第一步：先看一条边（一维，最容易看清）

源图只有 2 个像素：`[9, 1]`（左白右黑），放大 4 倍变成 8 个像素。

**Nearest —— 每个目标像素"抄"最近的源像素**

```
  源:  [ 9 ][ 1 ]

  放大 4 倍：
  9 9 9 9 | 1 1 1 1
  └────┬───┘
       ↑
   边界：从 9 直接跳到 1，中间没有任何过渡值 → 硬边、锐利
```

**Linear —— 边界处的像素做加权平均（双线性插值）**

```
  源:  [ 9 ][ 1 ]

  放大 4 倍：
  9 9 8 6 4 2 1 1
    │     │
    └─────┘
          ↑
   边界：冒出 8、6、4、2 这些"源里根本不存在的值" → 渐变、糊

  （这些数是按 u = (t+0.5)/4 − 0.5 定位后插值算出来的实数取整，
    关键在于：源里只有 9 和 1，插值却造出了 8/6/4/2）
```

**这就是两者的本质区别**：

```
  Nearest：目标像素的值 ⊆ 源像素的值集合    {9, 1}      → 不创造新颜色
  Linear： 目标像素的值可以是任意中间值      {9,8,6,4,2,1} → 创造新颜色
```

**"过渡色"这个说法很准，但要区分视觉与机制**：

```
  视觉：Linear 造出一圈过渡色 → 看起来"糊"了      ← 直观描述 ✅
  机制：那个"8"不是从调色板挑的，是加权平均算出来的  ← 准确机制 ✅

      8 = 9 × 0.25 + 1 × 0.75

  为什么放大倍数越大糊得越厉害？
  → 采样点落得越稀，需要跨更远的距离去平均
  → 平均的跨度越大，中间值越偏离原色
```

#### 第二步：回到二维，看到实际观感

源图 4×4（对角一条边），放大 2 倍 → 8×8：

```
  源（4x4）            Nearest（8x8）           Linear（8x8，实算）
  9 9 1 1             9 9 9 9 1 1 1 1        9 9 9 7 3 1 1 1
  9 9 1 1             9 9 9 9 1 1 1 1        9 9 9 7 3 1 1 1
  1 1 9 9             1 1 1 1 9 9 9 9        9 9 9 7 3 1 1 1
  1 1 9 9             1 1 1 1 9 9 9 9        7 7 7 6 4 3 3 3
                                           3 3 3 4 6 7 7 7
  边界是硬折线，                1 1 1 3 7 9 9 9
  值只有 9 和 1                1 1 1 3 7 9 9 9
                               1 1 1 3 7 9 9 9

  ★ Linear 里冒出了 7、3、6、4 这些源图里根本不存在的值
    → 这就是"糊"的本质：边缘被中间灰度填了
```

> 上表 Linear 为双线性插值实算结果
> （定位式 `u = (t+0.5)/zoom − 0.5`，边界 clamp）。

```
  用灰度看更明显（▓=亮 ░=暗 ▒=Linear 造出来的中间色）

  Nearest                     Linear
  ▓▓▓▓░░░░                   ▓▓▓▒▒░░
  ▓▓▓▓░░░░                   ▓▓▓▒▒░░
  ░░░░▓▓▓▓                   ▓▓▓▒░░
  ░░░░▓▓▓▓                   ▒▒▒▓▓▓
                             ▒▒▓▓▓
                             ░░▒▓▓▓

  只有 ▓ 和 ░，边界锐利          整条斜边被 ▒ 填满 → 发虚
  像素画风                      像蒙了一层灰
```

#### 第三步：本项目为什么默认 Nearest

```
  本项目是 176×220 的复古像素画，放大到 640×480 约 2.18 倍
  → 处在"放大倍数不大但已经看得出差别"的区间
  → 用 Linear 会把精心画的像素边缘糊掉，破坏原有美术风格
  → 所以 FilterMode 默认 Nearest（settings.rs:272）

  什么时候换 Linear？
    换成 HD 高清资源（feature hd-8bit）后
    或玩家手动在设置里切（玩家偏好，保留兜底）
```

**放大倍数与观感的关系**：

```
  1.0 倍  Nearest ≡ Linear（1:1 映射，根本用不到插值）
  2.18 倍 本项目场景 → 差别可见，Nearest 更合适（像素画）
  4 倍+   差别巨大 → 高清资源必须 Linear，否则锯齿明显
```

### 变换 3：本地坐标（**不是独立路径，是汇入画布**）

> ⚠️ 更正定位：本章早期版本把本地坐标写成"变换 3：本地 → 屏幕"，
> 暗示它是**并行的第三条变换路径**。这是错的——本地坐标解析完就变成画布坐标，
> **之后与视野坐标走完全相同的视口放大**，没有第二套缩放规则。

**正确关系**：

```
  世界(格) ──等距投影+摄像机──→ 画布(像素) ──视口放大──→ 屏幕
                                    ↑
                              本地坐标在这里汇入
                              （解析完归一为画布坐标）

  ★ 本地 = 相对某个参考物的偏移
  ★ 解析后的画布位置，和视野里的东西没有区别，一视同仁地放大
```

**生活类比：座位号 → 剧院里的具体位置**

```
   画布
   ┌──────────────────────────────┐
   │        ┌──────────┐          │
   │        │ 面板     │  面板在画布 (100, 100)
   │        │ ┌──────┐ │          │
   │        │ │ 按钮 │ │  按钮在面板内 (10, 20)
   │        │ └──────┘ │          │
   │        └──────────┘          │
   └──────────────────────────────┘

   解析：按钮画布位置 = 面板画布位置 + 按钮本地坐标
                     = (100, 100) + (10, 20)
                     = (110, 120)
                   ↓
        这一步之后就归一了，不再单独处理
```

**"同等放大"的意思**（关键）：

```
  面板画布 (100,100)，按钮本地 (10,20) → 按钮画布 (110,120)

  放大到屏幕（scale=2.18, offset=(128,0)）：
    面板 → (100×2.18+128, 100×2.18) = (346, 218)
    按钮 → (110×2.18+128, 120×2.18) = (368, 262)
                            ↑
      和视野里其他所有像素用同一个公式，没有例外
```

**图示：面板整体搬走，按钮跟着走**

```
   搬之前                        搬到 (200, 200)
   ┌────────────┐                ┌────────────────────────┐
   │ ┌────────┐ │                │        ┌────────┐      │
   │ │ 按钮   │ │                │        │ 面板   │      │
   │ └────────┘ │                │        │ ┌────┐ │      │
   │  面板      │                │        │ │按钮│ │      │
   └────────────┘                │        └────────┘      │
   (100,100)                     │        (200,200)       │
                                 └────────────────────────┘

   按钮本地坐标 (10,20) 两次都一样
   只有画布/屏幕坐标变了：(110,120) → (210,220)
```

**为什么只是平移**：UI 嵌套不需要自己的缩放，只需要"跟随参考物移动"。
`本地坐标 + 参考物画布位置 = 画布位置`，再统一走视口放大。

### 等距投影（Isometric Projection）

#### 一、最简直觉：为什么不用纯俯视

**一句话：俯视只能看到物体的顶面，等距能看到侧面。**

```
  俯视（正上方看）              等距（斜着看）

  ┌──────────────┐                ╱◆╲
  │  ○  ▲  □   │               ◆ ◆ ◆     ◆ = 树：看到树冠 + 树干
  │  ═══╪═══    │               ╲◆╱      ▲ = 人：看到头 + 身体
  │     │      │             ┌───┐       □ = 墙：看到墙面，有高度
  └──────────────┘             │   │
                                └───┘
  像看地图/蓝图                 像看真实场景

  ○ 人 = 只看到头顶            ○ 人 = 看到整个人
  □ 墙 = 只看到墙顶那条线       □ 墙 = 看到墙面，有高度
  │ 门 = 只看到门框顶部         门 = 看到门板
```

**所以"斜"不是为了好看，是为了看到侧面。** 纯俯视把世界压成了一张平面图，所有物体都只剩一个顶面，看不出立体感。

#### 二、为什么游戏用等距

```
  ① 用 2D 技术获得 3D 观感
     不用真 3D 引擎，一堆贴图就能做"RPG 俯视角"
     这是 90 年代至今 2D RPG 的标准做法

  ② 格子大小一致，地图好拼接
     等距没有近大远小，每个格子都是同样大的菱形
     → 贴图不需要按距离缩放，美术工作量小

  ③ 玩家能准确判断位置关系
     透视会扭曲远近感（远处的东西变小）
     等距不会，玩家看一眼就知道谁在前谁在后
```

#### 三、3D 游戏用等距吗？

```
  严格等距投影（平行投影）：现代真 3D 游戏基本不用

  真 3D 游戏用"透视投影"：
    有近大远小、平行线汇聚 → 更像人眼真实看到的世界
    例：CS、原神、任何 3A 游戏

  2D 等距游戏用"平行投影"：
    没有近大远小、平行线平行 → 看起来"不那么真实"但更"整齐"
    例：模拟城市4、Into the Breach、本项目
```

**但有个容易混淆的点**：

```
  "等距"这个词有两种用法：

  用法① 投影方法（数学）
    等距投影 = 正交投影 = 平行投影
    → 这是 2D 游戏的做法

  用法② 相机角度（视角）
    很多 3D 游戏把相机放在"类似等距的角度"，但渲染仍用透视
    → 暗黑破坏神3/4、流放之路 看起来像等距，其实是 3D + 透视 + 固定相机

  判断方法：
    看远处的东西会不会变小
    变小 → 透视（真 3D）
    不变 → 平行投影（2D 等距）
```

#### 四、几何原理（深入，可选读）

**等距不是透视，是平行投影。**

```
  透视（perspective）：              等距（isometric）：
  近大远小，平行线汇聚到灭点        没有近大远小，平行线在屏幕上仍然平行

  相机像眼睛看东西                  像用平行光把物体"拍扁"到屏幕上
  → 远处的房子变小                  → 远处和近处的房子一样大
  → 铁轨在远方汇聚成一点            → 铁轨永远平行，不会汇聚
```

**做法**：

```
  ① 把立体绕竖直轴（Z 轴）旋转 45°
  ② 从斜上方约 35.264° 俯视
  ③ 用没有近大远小的平行光，正交投影到 2D 屏幕
```

**35.264° 的来历**（实算验证）：

```
  俯角 = 90° − acos(√(1/3)) = 90° − 54.736° = 35.264°
       = 90° − atan(√2)

  这个特殊角度让 X、Y、Z 三个轴在屏幕上：
    · 长度相等（都是 1.0，实算验证）
    · 把平面分成 6 个 60° 的扇区
```

**"等距"名字的来源：三轴在屏幕上等长**

```
  X 轴 (1,0,0) → 屏幕 (0.866, 0.500)   右下
  Y 轴 (0,1,0) → 屏幕 (-0.866, 0.500)  左下
  Z 轴 (0,0,1) → 屏幕 (0, 1.000)       正上

  三条轴长度都是 1.0（实算验证）
  夹角：X-Y = 120°   X-Z = 60°   Y-Z = 60°
```

**屏幕上画出来**：

```
          Z 上
          |
  X 右下  |  Y 左下
   \     |     /
    \    |    /
     \   |   /
      \  |  /
       \ | /
        + 原点

  X 和 Y 在下方张开 120°
  Z 在正上方，与 X/Y 各成 60°
  三个轴把平面分成 6 个 60° 扇区
```

**"等距"的严格含义**：

```
  不是"所有边长都不变"
  而是：沿 X、Y、Z 三个主轴的单位线段，在屏幕上长度相等

  严格正交投影会让主轴缩短到 √(2/3) ≈ 0.8165 倍
  画等距图时通常整体放大 1/0.8165 ≈ 1.2247 倍补偿
  → 补偿后主轴在屏幕上又等于原始长度

  其他方向（对角线、斜边）的长度会变，这是正常的
```

**菱形的角度**：

```
  严格等距的菱形（地面正方格投影后）：

        /\
       /  \      ← 锐角 60°
      /    \
     \      /
      \    /     ← 钝角 120°
       \  /
        \/

  宽高比 = √3 : 1 ≈ 1.732 : 1

  游戏常用的 2:1 菱形（dimetric，不是严格等距）：

        /\
       /  \      ← 锐角 53.13°
      /    \
     \      /
      \    /     ← 钝角 126.87°
       \  /
        \/

  宽高比 = 2 : 1

  为什么用 2:1？
    → 像素能整数对齐（32 和 16 都是偶数）
    → 贴图好画，地图好拼
    → 视觉上仍然像等距
```

**本项目用的就是 2:1**（`ISO_X_STEP=32, ISO_Y_STEP=16`），属于 dimetric。

#### 五、环节：它在哪一步

```
  世界(格) ──① 等距投影──→ ──② 摄像机取景──→ 画布(像素)
             ▲ 这一步                    ▲ 这一步

  严格说 ①② 是同一步里的两个动作：
    等距投影 = 算出这一格落在画布哪里（步进 + y 翻转）
    摄像机   = 再减视野偏移、乘 zoom

  ★ 等距投影只管"格子朝哪歪"
    摄像机   只管"看哪一块"
    两者职责不重叠
```

#### 六、真实公式（`terrain_atlas.rs:162,167`）

```
  iso_x = 32 × (row + col)
  iso_y = 16 × (row + grid_w − 1 − col)
```

**两轴方向**（实算验证）：

```
  row+1 → (+32, +16)   斜下右 ↓   （往下 = 往前 = 近）
  col+1 → (+32, −16)   斜上右 ↑   （往右上 = 往远处偏）

  ★ 本项目的两条轴都朝"右"张开，整个地图是个菱形
```

**两种取向的比较**（初学者最容易懵的地方）：

```
  取向 A：教科书经典"V"形              取向 B：本项目"都朝右"
  一轴下右 + 一轴下左                   两轴都朝右（上右 + 下右）

         ╱◆╲                              ◆
       ◆◆   ◆◆                      ◆ ◆ ◆ ◆ ◆
     ◆◆       ◆◆                    ◆ ◆ ◆ ◆ ◆
                                       ◆ ◆ ◆ ◆ ◆

  轴间夹角 126.87°                      轴间夹角 53.13°
  地图像"菱形摊平"                     地图像"菱形立起"

  两种都是合法的等距变体，区别只在"哪个方向算屏幕纵向"
```

**为什么 `iso_y` 里有个 `grid_w − 1 − col`**：

```
  把 col 翻转：第 0 列落在 y 最大处（网格底部），最后一列落在 y 最小处
  → 地图"正过来"，玩家的角色朝上（屏幕上方）= 地图的上方
  → 这就是上面取向 B 的由来：两轴都朝右张开，顶部远、底部近

  正因为要做这个翻转，两轴才都朝右（而不是 V 形）
```

#### 七、实测：3×3 网格投影后长什么样

用真实公式渲染（`A`/`a` 交替区分相邻格）：

```
              ◆(0,2)                 ← 最上（col 最大）
      ◆(0,1)        ◆(1,2)
◆(0,0)      ◆(1,1)      ◆(2,2)        ← 中间一行，最左是 (0,0)
      ◆(1,0)        ◆(2,1)
              ◆(2,0)                 ← 最下（row 最大）

              ↓ 整体是个菱形
   最左 = (0,0)      最上 = (0, 2)
   最下 = (2,0)      最右 = (2, 2)
```

**对照俯视图**（3×3 正方格）：

```
  俯视图：方格，轴成 + 字形        等距图：菱形，轴都朝右
  ┌─┬─┬─┐
  │ │ │ │       row 向下 = 往下     row 向下 = 斜下右（靠近观察者）
  ├─┼─┼─┤       col 向右 = 往右     col 向右 = 斜上右（往远处偏）
  │ │ │ │
  └─┴─┴─┘
```

#### 八、单格算例（`grid_w = 16`）

```
  地图上有一格：row = 0, col = 2

  iso_x = 32 × (0 + 2)              = 64
  iso_y = 16 × (0 + 16 − 1 − 2)     = 208
                        └── 翻转 col，让第 0 列落在网格底部

  → 这一格落在画布 (64, 208)
```

**两轴方向的数值验证**（从 (0,0) 走一步）：

```
  row+1 → (32−0, 112−96) = (+32, +16)   斜下右 ↓
  col+1 → (32−0,  80−96) = (+32, −16)   斜上右 ↑
```

> ⚠️ 更正：本章早期版本写的是教科书通用式
> `sx = (wx−wy)×8` / `sy = (wx+wy)×4`（tile 16×8，两轴一左一右），
> **与本项目代码不符**。真实实现见上，步进是 32×16。

**为什么这样变换**：
- row 轴向右下（`iso_x` +32，`iso_y` +16）→ 往下 = 往前 = 更近
- col 轴向右上（`iso_x` +32，`iso_y` −16）→ 往右 = 更远一点
- 两轴一上一下张成菱形，产生纵深感

**z-order（绘制顺序）**：

```
  等距投影中，iso_y 越大 = 越靠"下" = 越近 = 越晚画（压在上面）

  因为 iso_y = 16 × (row + grid_w − 1 − col)
  等价于按 (row − col) 从小到大绘制
        row − col 越小 = 越远 = 先画

  画布从上到下（远 → 近）：
  ┌──────────────┐
  │ row−col 小(远)│  ← 先画
  │    ┌──────┐  │
  │    │  中   │  │  ← 再画
  │    │ ┌──┐ │  │
  │    │ │大 │ │  │  ← 最后画（压在上面）
  │    │ └──┘ │  │
  └──────────────┘
```

**反例警示**：

```
  画错（近的先画）：     画对（远的先画）：
     山                     人
   ┌────┐                 ┌────┐
   │    │                 │ 人 │  ← 人先画（远）
   │ 山 │  山盖住人       ├────┤
   │    │                 │ 山 │  ← 山后画（近），压住人下沿
   └────┘                 └────┘
   人不见了 ❌              层次正确 ✅
```

**本项目中的体现**：

```

crates/ti-app/src/scenes/main_map.rs — 按 iso_y 排序后逐格绘制（调用方）
docs/process/07_render_pipeline.md   — z-order 文件顺序与渲染管线契约
```

### 反向变换：物理 → 世界

#### 作用：它在解决什么问题

```
  回答玩家的问题："我点/摸的这一下，是点在哪个位置？"

    玩家点屏幕 → 要知道点中了地图哪一格
    玩家点 UI  → 要知道点中了哪个按钮

  正向变换：从地图画出画面
  反向变换：从画面找回归地图
  没有它，游戏就没法响应点击
```

#### 环节：它在整条链的哪一步

```
  整条链倒着走（严格逆序）：

  物理屏幕 ──① 逆视口──→ 画布 ──② 逆等距投影──→ 世界(格)
            除 scale、减 offset      解 u/v 方程

  若 zoom ≠ 1，还要在中间插一步：除 zoom、加视野位置

  ★ 顺序必须严格倒过来，颠倒或漏步都会算错
```

#### 完整闭环例子（实算验证过）

```
  起点：地图格 (row=0, col=2)，grid_w = 16

  正向走一遍：
    格 (0,2) ──等距投影──→ 画布 (64, 208)
                     ──视口────→ 物理 (267.6, 453.8)

  现在玩家真的点了物理 (268, 454)，反推回地图：

  ① 逆视口（除 scale，再减 offset）
       画布 x = (268 − 128) / 2.18 = 64.2
       画布 y = (454 − 0)   / 2.18 = 208.1
     → 画布 (64.2, 208.1)

  ② 逆等距投影（解方程组）
       u = 画布x / 32 = 2.01      ← u = row + col
       v = 画布y / 16 = 13.01     ← v = row + gw − 1 − col

       row = (u + v − gw + 1) / 2 = 0
       col = (u − v + gw − 1) / 2 = 2

  → 结论：玩家点的是地图 (0, 2) 格 ✅

  闭环校验：反算出的 (0,2) 再正算回画布 = (64, 208)
            与起点完全一致 ✅
```

**逆等距投影的公式怎么来的**（就是把正向方程组解出来）：

```
  正向：  u = row + col
          v = row + gw − 1 − col

  两式相加： u + v = 2·row + gw − 1  →  row = (u + v − gw + 1) / 2
  两式相减： u − v = 2·col − gw + 1  →  col = (u − v + gw − 1) / 2

  ★ 一步逆运算，不需要迭代搜索
```

#### 直观的正向链回顾

```
   玩家点的地方
        ▼
   ┌──────────────────────────────────────┐
   │░░░░┌──────────────┐░░░░░░░░░░░░░░░░░░│
   │░░░░│              │░░░░░░░░░░░░░░░░░░│
   │░░░░│      ● ← 点这里 (物理 150, 22)  │░│
   │░░░░│              │░░░░░░░░░░░░░░░░░░│
   │░░░░└──────────────┘░░░░░░░░░░░░░░░░░░│
   └──────────────────────────────────────┘

   倒着走（逆操作：先减后除，再除后加）
        │
        │ 减黑边 offset (128, 0)         ← 逆"加"
        ▼
   画布 (22, 22)
        │
        │ 除 scale (2.18)                 ← 逆"乘"
        ▼
   画布 (10, 10)
        │
        │ 除 zoom (1)，加视野位置 (40,20)  ← 逆"减+乘"
        ▼
   世界 (50, 30)
```

**逆向口诀**：

```
  正向：减位置 → 乘 zoom → 乘 scale → 加 offset
  反向：减 offset → 除 scale → 除 zoom → 加位置

           正向                          反向
    世界 ───────────→ 画布 ───────────→ 世界
```

**最简例子**（仅视口一层）：

```
  玩家点击物理像素 (150, 22)
    ① (150 − 128) / 2.18 = 10.1 ≈ 10     → 画布 (10, 10)
    ② 10 / 1 + 40 = 50, 10 + 20 = 30    → 世界 (50, 30)
```

**常见错**：忘了减 `offset`（黑边）就直接除 `scale`，
点在黑边上会算出负数坐标。逆操作必须**严格倒序**。

## 常见坑

| 坑 | 原因 | 避免 |
|---|---|---|
| 触摸坐标没转换 | 直接用物理像素当逻辑坐标 | 触摸 → 视口反变换 → 逻辑坐标 |
| 视野抖动 | 视野位置每帧变化 | 视野位置只在玩家移动时更新 |
| 等距投影 z-order 错误 | 绘制顺序不对 | 按 `row − col` 排序绘制（等价于 `iso_y` 升序） |
| 照抄教科书等距公式 | 通用式 `sx=(wx−wy)×w/2` 与本项目不符 | 用 `terrain_atlas.rs` 的 `iso_x` / `iso_y` |
| 格与像素比例记错 | 以为 1 格 = 1 像素 | 本项目每格步进 32×16 画布像素 |
| 黑边当成 bug | `Smooth` 模式本就会留边 | 想无黑边切 `ZoomCrop` / `Stretch` |
| 放大后画面发糊 | 像素画用错 `FilterMode` | 复古像素用 `Nearest` |
| 本地坐标当成独立变换路径 | 误以为它有一套自己的缩放 | 解析归一为画布坐标，之后与视野坐标同等放大 |
| 反向变换顺序颠倒 | 先除 scale 再减 offset | 严格逆序：减 offset → 除 scale → 除 zoom → 加位置 |
