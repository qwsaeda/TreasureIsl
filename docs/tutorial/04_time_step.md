## 核心概念

### 问题：可变时间步长的缺陷

```
想象你开车，换挡时机不同：
  低速挡（30 FPS）：1 秒走 8 米
  高速挡（60 FPS）：1 秒走 16 米

  时间过了 1 秒，但走的距离不一样！
  → 帧率不同 = 同样的"每秒"跑的距离不同 = 游戏速度不一致
```

**游戏也一样**：如果 update 每帧直接移动固定距离，帧率不同 = 游戏速度不同。

```
  可变时间步长的问题（每帧固定移动 10 像素）

  60 FPS：  ■━━●━━■━━●━━■━━●━━■━━●━━■━━●
           60 帧 × 10 = 每秒 600 像素

  30 FPS：  ■━━━━━━━━━●━━━━━━━━━●━━━━━━━━━●
           30 帧 × 10 = 每秒 300 像素
           ▲
           每帧的步子一样长，但帧少 → 跑得慢一半 ❌

  同样过 1 秒，60 FPS 的玩家走远了，30 FPS 的还在原地附近。
```

### 解决：固定时间步长

```
想象你开车定速巡航：
  不管路况（帧率），速度表显示 60 公里/小时
  同样开 1 秒，走的距离相同

  实现：把时间切成固定的小块（1/60 秒），每块移动固定距离
  帧率快 → 每帧可能执行 1 块或 0 块
  帧率慢 → 每帧可能执行多块
  但每块的时间固定，速度就固定
```

**把 1 小时切成 60 份，每份 1 分钟**：

```
  60 FPS：  ├─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┤
            每帧 = 1 份 → 每帧 update 1 次

  30 FPS：  ├───┼───┼───┼───┼───┼───┤
            每帧 = 2 份 → 每帧 update 2 次

  144 FPS： ├┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼├
            每帧 = 0.42 份 → 有的帧 update 0 次，有 1 次

  ★ 关键：不管几帧，每次 update 都只走"1 分钟"的量。
    30 FPS 每帧走 2 次 × 1 份 = 2 份
    60 FPS 每帧走 1 次 × 1 份 = 1 份
    但每秒都是 60 份 → 速度一致 ✅
```

### 累积器模式

```
想象一个水桶（累积器），桶上有个刻度线 = 1/60 秒

  60 FPS                          30 FPS
  ┌─────────┐ ← 刻度线            ┌─────────┐ ← 刻度线
  │░░░░░░░░░│                      │░░░░░░░░░│
  └────┬────┘                      └──┬───┬──┘
       │每帧倒入                    每帧倒入 2 份
       ▼                               ▼   ▼
  ███ 满 → 倒掉 → update(1/60)     ███████ 满了两次
  桶空了 → 等下帧                  → update ×2 → 桶空

  ★ 不管倒入多少，update 的步长永远是 1/60 秒。
    桶只负责"记账"，保证该走多少步就正好走多少步。
```

**144 FPS 的情况**：

```
  桶没满，但还是要出画面 → 这时就用插值（见下节）
```

### 渲染插值（Interpolation）

```
问题：144 Hz 显示器，逻辑只有 60 Hz 更新
  → 有些渲染帧看到的是同一个状态 → 画面卡顿

  144 FPS 下连续 2~3 个渲染帧，逻辑位置都是 X
        帧1: X      帧2: X      帧3: X        ← 看起来卡
        帧4: X'  ← 逻辑终于推进了

解决：桶里的"零头"告诉你该显示在 X 和 X' 之间的哪个位置
```

**插值图解**（桶里剩了 0.42 份）：

```
  位置轴：
  X ├────────────────────● X'
                        ▲
                     当前画面画在这

  插值位置 = X × (1 − α) + X' × α      其中 α = 桶里剩余 / 1份 = 0.42

  0 ━━━━━━━━━●━━━━━━━━━━━━━━━━━━━━━ 1
             α = 0.42
             离 X 近一些（因为上一帧的位置权重更大）

  → 每次渲染都画在"两帧之间"，看起来就是平滑移动 ✅
```

> 注意 α 的方向：`α` 越大越靠近 `X'`（新状态）。
> 桶越满 = 离下一次逻辑更新越近。

### 两种模式对比

| 模式 | 生活类比 | 复杂度 | 确定性 | 适合 |
|---|---|---|---|---|
| 可变时间步长 | 油门时轻时重 | 低 | 否 | 原型验证 |
| 固定时间步长 | 定速巡航 | 中 | 是 | 需要复现的游戏 |
| 固定步长 + 插值 | 定速巡航 + 平滑 | 高 | 是 | 高刷新率项目 |

## 项目对照

### 本项目时间处理

```
crates/ti-app/src/game_app.rs  — set_frame_delta_ms
crates/ti-app/src/bin/treasure_native.rs — tick_frame_time
```

### 本项目选择

本项目**没有**使用固定时间步长 + 累积器模式。原因是：

1. **回合制游戏**：大多数操作是离散的（按键 → 移动一格），不需要物理模拟的连续性
2. **帧驱动动画**：`set_frame_delta_ms` 只用于推进精灵动画（如战斗动画的帧推进）
3. **简单性**：可变时间步长对回合制游戏足够，引入累积器增加复杂度

### 帧时间的使用场景

帧时间在本项目中用于：
- 精灵动画推进（战斗特效帧）
- FPS 统计（`stats` feature）
- 帧耗时监控

### 练习 2：实现累积器

用伪代码实现固定时间步长 + 累积器：

```
固定时间 = 1/60 秒
累积器 = 0

每帧：
  实际耗时 = 过了多久
  累积器 += 实际耗时
  当累积器 >= 固定时间：
      update(固定时间)
      累积器 -= 固定时间
  渲染(累积器 / 固定时间)
```

## 常见坑

| 坑 | 原因 | 避免 |
|---|---|---|
| 游戏速度随帧率变化 | 可变 dt 直接用于位移 | 固定时间步长 |
| 螺旋死亡（Spiral of Death） | 一帧内 update 次数过多 | 限制最大 update 次数 |
| 动画卡顿 | 动画帧率与逻辑帧率不匹配 | 动画用独立时间轴 |
| 浮点累积误差 | 长时间运行后 dt 漂移 | 用整数毫秒或定点数 |
