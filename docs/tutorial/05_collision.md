## 一、为什么需要碰撞检测

**先想一个问题：如果游戏里完全没有碰撞检测，会怎样？**

```
  你控制角色往墙走  → 角色直接穿过墙，走出地图 ❌
  你点屏幕按钮      → 手指点哪里都没反应，游戏没法操作 ❌
  你射出子弹        → 子弹穿过敌人，敌人不受伤 ❌
  你摇骰走到宝藏格  → 不知道到了，金币拿不到 ❌

  碰撞检测一加上：
  走到墙边停下 ✅  点中按钮触发 ✅  子弹击中扣血 ✅  落格自动结算 ✅
```

**一句话：碰撞检测 = 判断"两个东西碰了 / 到了 / 重叠了没有"。**
没有它，游戏就变成一幅**不能互动的画面**。

生活类比：你在街上走，不能穿过墙壁——你的身体和墙壁做了一次"碰撞检测"。
游戏里只是把这件事从身体换成了代码。

**三大用途（本项目）**：

| 用途 | 在问什么 | 本项目 |
|---|---|---|
| 移动限制 | "我能走到这格吗" | ~~自由格~~（已删）→ 环岛赛道 |
| 交互命中 | "我点的是哪个按钮" | ✅ AABB（`main_map.rs`） |
| 事件触发 | "我落到哪格、发生什么" | ✅ 落格结算（`rules::board`） |

## 二、碰撞检测的本质：三种形状三种方法

所有碰撞检测，不管多复杂，都在回答**"有没有重叠"**。区别只在于**形状不同 → 判断方法不同**。

| 形状 | 方法名 | 核心判断 | 计算量 |
|---|---|---|---|
| 两个矩形 | **AABB** | 4 次边界比较 | 最多 4 次 |
| 两个圆 | **圆碰撞** | 距离² < 半径和² | 1 次平方和 |
| 网格格 | **查表** | 格子的值是否为 0 | 1 次数组索引 |

> **AABB 全称 = Axis-Aligned Bounding Box（轴对齐包围盒）**
> "包围盒" = 用一个最小矩形把物体框住；"轴对齐" = 矩形边平行于坐标轴（不旋转）。
> 生活类比：把东西装进刚好卡住的纸箱，纸箱边不歪不斜。

## 三、从一维到二维：基础建立

**这是所有方法的地基。二维 = 把一维做两遍（x 轴一遍 + y 轴一遍）。**

### 一维：数轴上的两段线

```
  线段 A：0 ~ 10
  线段 B：5 ~ 15

  判断（2 次比较）：
    A 右(10) > B 左(5)？  ✅
    A 左(0)  < B 右(15)？ ✅
    两次都成立 → 有重叠

  不重叠：A 0~4，B 10~15
    A 右(4) > B 左(10)？ → 4 > 10 不成立 → 隔开了

  边界（容易写错）：A 0~10，B 10~15
    A 右(10) > B 左(10)？ → 10 > 10 不成立 → 贴边不算重叠
```

**记住：一维 = 2 次比较。二维 = 两个方向 × 各 2 次 = 4 次。**

## 四、方法 1：AABB（二维矩形）

**生活类比：两张扑克牌是否叠在一起**

![AABB 示意图：两个矩形 + 4 次边界比较](../../evidence/tutorial/05_aabb_concept.png)

### 例子

```
  牌 A：左上角 (0,0)，10×10 → 左=0  右=10  上=0  下=10
  牌 B：左上角 (5,5)，10×10 → 左=5  右=15  上=5  下=15
```

### 4 次比较逐一拆

**核心思想：把二维拆成两个一维。x 轴查一遍，y 轴查一遍，各 2 次。**

**x 轴（水平）—— 问"A 是否完全脱离 B"：**

| 问 | 算 | 结果 |
|---|---|---|
| A 完全在 B 左边？ | A右(10) ≤ B左(5)？ | 10 ≤ 5 **不成立** |
| A 完全在 B 右边？ | A左(0) ≥ B右(15)？ | 0 ≥ 15 **不成立** |

两次都不成立 → A 没有"完全脱离" B → x 方向有重叠 ✅

**y 轴（竖直）—— 同样问 2 遍：**

| 问 | 算 | 结果 |
|---|---|---|
| A 完全在 B 上边？ | A下(10) ≤ B上(5)？ | 10 ≤ 5 **不成立** |
| A 完全在 B 下边？ | A上(0) ≥ B下(15)？ | 0 ≥ 15 **不成立** |

两次都不成立 → y 方向有重叠 ✅

**汇总：4 次全"不成立" → 两个方向都重叠 → 牌叠在一起 ✅**

> **为什么是 4 次不是 2 次？** 一维 = 2 次（左/右各一次），二维有两个方向 = 2×2 = 4。
> **短路**：任何一个方向"完全分开"（某次成立），立刻退出不重叠，不用做完 4 次。

### 完整公式

```
  重叠 = (A右 > B左  且  A左 < B右)    ← x 方向重叠
       且 (A下 > B上  且  A上 < B下)    ← y 方向重叠
```

### 不重叠的例子（短路，只用 1 次）

```
  A：左=0  右=4     B：左=10  右=15
  A 完全在 B 左边？ A右(4) ≤ B左(10)？ → 4 ≤ 10 成立 → A 完全在 B 左边 → 不重叠，退出
```

### 重叠面积

```
  交集 x = [max(0,5), min(10,15)] = [5,10]，宽 5
  交集 y = [max(0,5), min(10,15)] = [5,10]，高 5
  面积 = 5×5 = 25（本项目只关心"有/无"，不关心面积）
```

### 为什么叫"轴对齐"？

```
  轴对齐 = 矩形边平行于坐标轴（不歪不斜）

  ┌────────┐           ╱────────╲
  │  按钮  │          ╱   按钮    ╲     ← 斜着放 → AABB 不适用
  └────────┘          ╲            ╱         （要用 SAT 等更复杂的方法）
  正常，AABB 够用

  本项目 UI 按钮全是轴对齐的（水平放置），AABB 够用。
```

### 本项目实码（`main_map.rs:471-478`，节选 + 注释）

```rust
// 触摸点 (px, py) 是否落在 scenes.json 中名为 key 的按钮矩形内？
let hud_hit = |key: &str| -> bool {
    l.extra.get(key).is_some_and(|r| {
        r.w > 0
            && r.h > 0
            && (r.x..(r.x + r.w)).contains(&px)   // x ∈ [x, x+w)
            && (r.y..(r.y + r.h)).contains(&py)   // y ∈ [y, y+h)
    })
};
```

> `(r.x..(r.x + r.w)).contains(&px)` = `px ≥ r.x 且 px < r.x + r.w`（左闭右开）
> 实际调用：`main_map.rs:486`（`hud_hit(DECK_SPIN)` = 摇骰 CTA）
> 命中判定均内联在各场景 `on_touch`（L459 起）方法中，无独立 `hit_test` 函数。

## 五、方法 2：圆形碰撞

**生活类比：两个泡泡是否碰到一起**

![圆形碰撞：距离² < 半径和² 判断](../../evidence/tutorial/05_circle_collision.png)

```
  泡泡 A：圆心 (0,0)  r=5
  泡泡 B：圆心 (8,0)  r=5

  判断（用平方避免开根号）：
    距离² < (半径A + 半径B)²
    8² < (5+5)²
    64 < 100 → 碰到了 ✅

  拉开：B 圆心 (12,0) → 144 > 100 → 没碰到 ❌
```

**本项目不用圆形碰撞**——UI 里的圆形形状（罗盘环/圆角铜牌）渲染时是圆的，
但**命中区仍是矩形 AABB**（`dx <= hit_r && dy <= hit_r`，本质方形）。
理解圆碰撞有助于理解为什么"子弹击中"类用距离平方判断。

## 六、方法 3：网格查表（最简的"碰撞"）

**生活类比：棋盘上问"这个格子能不能走"**

![网格查表：玩家四方向查表判定可走/被挡](../../evidence/tutorial/05_grid_lookup.png)

```
  地图 = 二维数组，每格一个值：0 = 空地（能走），1 = 墙（不能走）

  玩家 (行2, 列2) 查 4 个邻格：
    南 地图[3][2] = 0 → 能走 ✅
    西 地图[2][1] = 1 → 被挡 ❌
    东 地图[2][3] = 0 → 能走 ✅
    北 地图[1][2] = 1 → 被挡 ❌

  一次下标 + 一次值比较 = O(1)，无几何计算
```

> 本项目**不再用自由格移动**（S19.1 方向键已删除）。
> 网格数据仍用于地形渲染（画哪些格是陆地/礁石），移动规则已改为环岛赛道。

## 七、本项目的碰撞：环岛赛道（S19）

**上面的三种方法，本项目主地图移动都不直接用。实际玩法是"大富翁式摇骰"。**

**生活类比：大富翁掷骰子**

```
  玩家在环路上，面朝前方
  掷骰子 → 走 N 格 → 落到哪个格就停
```

### 赛道数据（`assets/data/board.json`）

```
  每图一条闭合环（顺时针）：m01=45格  m02=46格  m03=33格
  每格类型：start / plain / port / city / event / card / battle / treasure / boss
```

### 摇骰 + 前进 + 落格结算（`rules::board`）

```
  ① 摇骰：step = rng(1..=6)
  ② 前进：pos = (pos + step) % 格数；绕起点 → lap+1（奖励金币）
  ③ 落格结算（只认终点格，路过不结算）：
    port     → 提示"可贸易/建造"
    city     → +50 金
    event    → 抽一张卡
    card     → 抽一张卡
    battle   → 扣 30 HP + 失 20 金
    treasure → +200 金
    boss     → 绕满 boss_min_laps 圈后经过/落格才进战斗（见拦停规则）；未满圈只提示
    plain    → 无事
```

**"碰撞"在这个模型里 = 格类型查表 + 结算**，不是几何碰撞。

### BOSS 拦停规则（S19.3）

```
  经过或落在 BOSS 格 → 触发战斗
  但需绕满 boss_min_laps 圈（默认 1）才现身
  未满圈 → 提示"BOSS 尚未现身（还需绕 N 圈）"，不进场景

  为什么"经过即遇"而非"恰好落格"？
    33~46 格赛道，恰好落格 ≈ 1/40 概率 → 期望 32~41 次摇骰
    改为经过即遇 → 期望 16~21 次，节奏收敛
```

### 实码位置

```

crates/ti-core/src/rules/board.rs:315  — advance_one()（前进一格 + 绕圈计 lap）
crates/ti-core/src/rules/board.rs:343  — step()（一次摇骰回合 + BOSS 判定）
```

## 常见坑

| 坑 | 原因 | 避免 |
|---|---|---|
| 以为主地图是自由格移动 | S19.1 已删方向键 | 只保留摇骰（`GameInput::Spin`） |
| 落格结算用了路过格 | 大富翁语义：只有终点结算 | 只看 `(pos+step) % len` |
| BOSS 要"恰好落在" | S19.3 改为经过即遇 | 绕满 `boss_min_laps` 圈后经过即触发 |
| AABB 用 `>=` 代替 `>` | 贴边也算重叠 | 严格 `>`（10 > 10 不成立） |
| 格索引用 float | 整数格无浮点误差 | `usize`/`i32` |
| 每帧全量扫描赛道 | 赛道只有 33~46 格 | 直接查 `board[pos % len]`，O(1) |
