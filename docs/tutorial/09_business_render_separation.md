- [ ] 理解业务逻辑与渲染分离的原则

## 核心概念

### 为什么要分离

**生活类比：厨师和摆盘师**

```
厨师（业务层）：做菜
  决定菜的味道、配料、烹饪时间
  不关心盘子长什么样

摆盘师（渲染层）：摆盘
  决定菜怎么摆、盘子怎么放
  不改变菜的味道

  好处：
    换厨房（渲染后端）→ 厨师不用改
    换菜单（业务逻辑）→ 摆盘师不用改
    厨师可以盲测菜的味道（单元测试）
```

**不分离的问题**：
```
厨师既要炒菜又要摆盘：
  - 换厨师 → 摆盘风格可能变
  - 换盘子 → 厨师可能改炒菜方式
  - 无法单独测试"菜的味道"
```

### 分离的原则

```
业务层（ti-core）：
  - 不依赖任何渲染 API
  - 输出渲染所需的数据（状态）
  - 可单元测试（像厨师盲测味道）

渲染层（ti-app / ti-platform）：
  - 只读取业务层的数据
  - 不修改业务状态
  - 可替换实现（像换摆盘师）
```

### 渲染指令模式

**生活类比：厨师写菜谱，摆盘师照做**

```
厨师不亲手摆盘，而是写菜谱：
  1. 在盘子左上角画一条红线
  2. 在盘子中间放一块肉
  3. 在盘子右下角撒葱花

摆盘师照做：
  收到菜谱 → 一步步执行 → 摆好盘

  好处：
    厨师不用关心盘子材质（渲染后端）
    摆盘师不用关心菜谱味道（业务逻辑）
```

**形式化**：
```
业务层输出渲染指令：
  画精灵 { 位置 (10, 20), 图片编号 5 }
  画文字 { 位置 (5, 5), 内容 "金币: 1000", 颜色 白色 }
  填充矩形 { 位置 (0, 0), 宽 176, 高 20, 颜色 蓝色 }

渲染层执行指令：
  收到指令 → 画到帧缓冲 → 上传 GPU
```

### 事件注入

**生活类比：服务员传菜**

```
服务员（渲染层）：把菜单送到厨房
  客人点菜 → 服务员记下 → 告诉厨师

厨师（业务层）：做菜
  收到菜单 → 做菜 → 出菜

服务员（渲染层）：上菜
  收到菜 → 摆盘 → 上桌

  服务员不改变菜的味道（业务状态）
  厨师不关心怎么摆盘（渲染细节）
```

**游戏中**：
```
渲染层：捕获按键 → 转换为业务事件 → 注入业务层
业务层：处理事件 → 更新状态 → 输出新状态
渲染层：读取新状态 → 绘制
```

## 项目对照

### 分层架构

```
crates/ti-formats/    — 格式层（pak/PCX/字体/地图/存档解析）
crates/ti-core/       — 业务层（零 IO，可单测）
crates/ti-platform/   — 平台层（渲染/输入/音频/存储抽象）
crates/ti-app/        — 表现层（场景/控件/输入/四端 bin）
```
（层序以 `Cargo.toml` 实测为准；详见第 10 章与 `docs/process/01_architecture.md` §1）

### 业务层零 IO

```
crates/ti-core/src/lib.rs
```

```
硬约束：不依赖任何平台/IO 后端，只依赖 ti_formats
因此可以在无窗口环境跑差分测试与全流程回归
```

### 渲染指令模式

```
crates/ti-app/src/scenes/ — 各场景的 render 函数
```

场景的 `render` 函数读取 `GameApp` 状态，输出到帧缓冲：

```
读取业务状态：
  当前金币 = 1000
  玩家位置 = (50, 30)

输出到帧缓冲（渲染指令）：
  填充矩形 (0, 0, 176, 20) 颜色 蓝色
  画文字 (4, 4) "金币: 1000" 颜色 白色
```

### 事件注入

```
crates/ti-app/src/scenes/mod.rs — route_input
```

```
渲染层捕获输入 → 注入业务层
```

### 本项目的分离特点

1. **业务层零 IO**：`ti-core` 不依赖 `ti-platform` 或 `ti-app`
2. **渲染层只读**：场景通过 `SceneHost` trait 读取业务状态
3. **输入事件注入**：渲染层捕获输入，通过 `route_input` 注入业务层
4. **多端复用**：同一 `ti-core`，不同 `ti-app` bin（native/wasm/android/headless 共 4 个运行端，
   另有 element-dump / sprite-step 等离线工具 bin）

- 为什么用 trait 而不是直接传引用？
- 8 个子 trait 的拆分有什么好处？

### 练习 3：设计渲染指令

如果要把本项目改成显式渲染指令模式，需要：
- 定义"画精灵""画文字""填充矩形"等指令
- 业务层输出指令列表
- 渲染层执行指令

思考：这种模式比直接调用渲染 API 有什么好处？有什么坏处？

## 常见坑

| 坑 | 原因 | 避免 |
|---|---|---|
| 业务层依赖渲染 API | 没有分离 | 业务层零 IO |
| 渲染层修改业务状态 | 违反只读原则 | 渲染层只读 |
| 输入处理在渲染层 | 业务逻辑在渲染层 | 输入事件注入业务层 |
| 无法单元测试 | 业务依赖渲染 | 分离后可测试 |
